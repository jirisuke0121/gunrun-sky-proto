# 見た目の重さ A/B計測 #2：11/10の見た目に全部戻す（2026-11-20）

## なぜ作ったか

`bench/ab-glow-outline.html`（太陽グロー・輪郭線・塵・接地影・遠景を1つずつ消す）をiPhoneで測った結果（`docs/AB_GLOW_OUTLINE_2026-11-20.md`）：

- 8条件すべてが判定不能。誤差幅（約±1〜1.5ms）が差より大きい。
- 基準に入れた「描画解像度×0.75」（画素が約44%減る）ですら +1.10ms ±1.45 で判定不能。確実に効く変更を検出できない精度だった。
- よって **「どれも誤差」ではなく「この精度では差が見えなかった」** と読む。1つずつの合計（+3.32ms）と5つまとめ（+0.93ms）が合わないのも、数字がほぼ誤差で動いている証拠。

小さい部品を1つずつ消しても埋もれるので、**まとめて戻す1条件**にして検出力を上げる。

## 測り方

`bench/ab-look-classic.html`（開くだけで自動。約5〜6分）。

- A＝今の見た目（`index.html`）／B＝11/10相当（`index.html?look=classic&mood=noon&outline=0&windFx=0`）。
  - `look=classic`：漆喰シェーダー・建物の色・床のむら・接地影が従来。
  - `mood=noon`：低い朝日・太陽グロー・遠景・塵なし。
  - `outline=0`：輪郭線なし。 `windFx=0`：風の筋なし。
- 切り替えにはゲームの読み込み直しが要る。ラウンドごとに A→B／B→A を入れ替え（時間経過・発熱の偏りを相殺）、**12ラウンド**（既定。前回は6）。
- 読み込みのたびにiframeを作り、WebGLを `forceContextLoss` で手放して捨てる（24回作り直してもメモリが溜まらないように）。
- 1回の読み込みの中で「描画解像度×0.6」の対照も測る。確実に効く変更を検出できているかの目安。
- 差を増幅する K回の余分描画、停止検知（400ms超は除外）、1割超が停止なら区間やり直し、は前回と同じ。
- 結果の最後に、描画命令数・三角形数と「切り替えが効いたか」（輪郭線0・グロー0など）を出す。

## 読み方（結論の出し分け）

差＝「今の見た目 − 11/10相当」（1回の描画あたりms。正なら今のほうが重い）。

| 結果 | 読み |
|---|---|
| t≥2 かつ 3ms以上 | 今の見た目が原因。次は、戻した中の何が効いたかを絞る |
| t≥2 かつ 1〜3ms | 見た目が重くしているが、主因とまでは言えない |
| t≥2 かつ 0.3〜1ms | 見た目はほぼ無実 |
| 有意でなく、検出限界（±2×標準誤差）が1ms未満 | 差は見えなかった＝見た目はほぼ無実 |
| 有意でなく、検出限界が1ms以上 | 判定不能。ラウンドを増やすか冷めてから測り直す |

見た目が無実なら、残る原因はマップ側（11/10〜11/11に足した中央屋上の溝と柵、窓、大スイングと窓破り）、11/13の復帰ロープ、影・アンチエイリアス、ゲーム処理。

## 記録は送らない

iframe の `fetch` / `sendBeacon` を止め（返事は「保存済み」）、計測後はiframeごと捨てるのでゲームは終わらない。2026-11-20に前回のページで本番ランキングに記録が2件入った事故（`docs/AB_GLOW_OUTLINE_2026-11-20.md`）の再発防止。

## 確認したこと／していないこと

- 確認済み（手元のヘッドレスChrome＝ソフトウェアGL）：AとBが実際に切り替わる（B側は look=classic・mood=noon・輪郭線／グロー／遠景／塵／接地影が0）、描画命令数は今552→戻し547でほぼ同じ、三角形は約157k→144k、POST 0件、iframeが残らない、統計が出る。
- 確認していない：iPhone実機での数値。ソフトウェアGLの時間はGPUの重さとして意味がない。
- 目安：1回の読み込み約8秒（ソフトウェアGL）。実機のほうが速いかもしれないが、24回なので数分かかる。
